# 可靠上下文缓存：面试讲解稿

这次解决的是：Agent 连续做任务时，每个回合都要准备角色资料、用户记忆、会话消息和技能信息，如果反复从数据库和对象存储读取，会产生重复 I/O。我们缓存这些上下文原料，同时解决数据更新、缓存故障和技能换版的问题。

## 可以直接说的开场

> 我给 Agent 的上下文准备过程加了缓存，主要缓存角色资料、用户记忆、当前会话工作集和技能信息。数据库仍然保存正式数据，Redis 负责加速。
>
> 我没有只做缓存命中，还处理了数据变化后的失效、通知失败后的补偿，以及并发情况下旧数据覆盖新数据的问题。
>
> 技能采用版本化发布：完整上传后再切换版本，每个回合固定使用一份技能快照。因此本轮不会用到一半突然换版本，新安装或更新的技能正常发布后，下一轮就能使用。

## 1. 缓存了什么

| 内容 | 通俗理解 | 存放位置 |
| --- | --- | --- |
| Agent 的角色、行为等 MD 资料 | 它是谁、该怎么做事 | Redis |
| USER.md、MEMORY.md 等用户资料和记忆 | 当前用户是谁、有哪些偏好和已知信息 | Redis |
| 当前会话工作集和必要元信息 | 这一轮接着往下执行所需的消息，包括工具调用、多模态字段等 | Redis |
| 技能使用与生命周期状态 | 哪些技能用过、是否参与当前技能列表等依据 | Redis |
| 技能发布清单 | 有哪些技能、每个技能当前发布的是哪个包 | Redis |
| 资料缺失时查找 Agent 所有者的结果 | 按原有规则寻找默认资料，不把不同用户的数据混到一起 | Redis |
| 技能文件和解析后的说明 | 包下载到本地，说明不用每次重复解析 | 本地目录和进程内缓存 |
| 同一个回合的资料读取结果 | 系统提示和附加提醒共用已经读到的资料 | 本轮内存快照 |

会话缓存的是当前可压缩工作集 `sessions.messages`，不是把全部归档历史重新加载。技能文件本体不整包塞进 Redis，Redis 主要缓存包清单。

没有缓存模型最终答案、完整模型请求、所有工具执行结果、RAG 检索结果或执行器/回合锁。缓存不会自动减少发给模型的 token；主要减少准备上下文时的重复读取。

## 2. 一般怎么读写

读的时候先看 Redis，有就直接用；没有就读正式存储，并尝试放回缓存。多个相同的并发请求在同一进程内合并回源，避免一起访问数据库。返回结果也避免共享可被别人修改的消息切片。

写的时候先提交数据库，再让旧缓存失效。这里的“通知缓存”主要就是让旧副本不能再被使用，不是删除数据库里的业务内容；会话还会从已经提交的数据库内容更新缓存。

## 3. 为什么把过期时间改成 30 分钟

连续多个回合可以复用缓存，60 秒对长任务太短。30 分钟是默认缓存保留时间，读一次不会重新续命。即使偶尔漏掉失效，旧数据也不会因为一直有人读就永远留着。

它既不是任务超时，也不是技能更新要等待的时间。任务可以执行几小时，当前回合固定的技能仍可使用；正常发布通过主动失效让下一回合看到新技能。

## 4. 更新通知失败怎么办

可以把它想成“修改资料时，顺便在数据库里写一张待办单：这份缓存要更新”。资料修改和待办单在同一个事务里成功或失败，不会资料已经改了、通知却从此找不到。

后台定期检查待办单，失败就留着重试。处理成功才标记完成；同一份数据连续改很多次，可以合并为更新到最新版本，避免把每次修改排成长队。这就是这里的 outbox 补偿。

数据库触发器统一记录变化，因此不只某个网页接口能触发，后台任务和直接 SQL 内容更新也能被记录。不过直接 SQL 的传播通常走后台补偿，不等同于所有入口都同步即时刷新。

## 5. Redis 挂了会怎样

受影响实例改为直接读数据库，不因为加速层坏了就让本已成功的数据写入失败。缓存操作有短超时；恢复后先补完待办通知，再恢复缓存读取。缓存里的内容损坏或格式不认识时，也会回源。

当前部署用独立的 Redis，设置内存上限；满了可以淘汰冷缓存，丢掉后再从正式存储加载。调度 Redis 单独保留，不与上下文缓存竞争同一实例的淘汰空间。

这是可恢复的最终一致性。局部网络故障时，其他仍连着旧缓存的实例可能短暂看到旧数据，不能说成任何情况下都零延迟一致。

## 6. 旧请求会不会把旧内容重新塞回缓存

例如：A 开始读旧数据，还没放回缓存；B 已经把资料更新并让旧缓存失效；A 最后才回来。

我们给缓存加了版本和“本次填充资格”校验。A 拿的是旧资格，就不能覆盖 B 之后的状态。缓存过期、淘汰或 Redis 重启后，迟到的旧请求也不能借机重新建立旧副本。

面试可以叫“版本校验和防止旧请求回填”，不用展开 Redis 脚本细节。

## 7. 如何避免聊天记录被旧副本覆盖

读会话时一起带上版本，保存时核对数据库版本。如果别人已更新，旧写入被拒绝，并停止继续请求模型或执行后续工具，要求重新加载；不会自动重放可能产生副作用的工具。

这次特别修复了三类边界：查到“会话不存在”后别人刚创建会话，不能拿空消息覆盖；清空后别人并发重建，不能丢掉对方消息；只改聊天标题，不应让正在生成的回答保存失败。

版本校验保护数据写入，不等于已经做了跨机器的完整执行锁或任务迁移。

## 8. 技能为什么不会只更新一半

先准备完整的技能包，上传所有文件；全部成功后，才把数据库中的“当前版本”切换到新包。上传失败就继续用旧包。

文件按内容指纹保存，下载时也核对指纹，避免错包或损坏文件。新版本放进新目录，不直接改旧版本的文件；受控 edit_file/write_file 也是复制、修改、发布。

## 9. 新增或更新技能，下一回合如何生效

按下面四步讲最清楚：

1. 本轮开始时，读取当前技能清单，并固定这一轮使用的具体版本。
2. 运行过程中安装或更新技能，完整包发布成功后立即让旧清单缓存失效。
3. 本轮的技能摘要、load_skill 和沙箱仍使用原先固定的版本，不会中途变样。
4. 下一轮重新读取清单、固定新的版本；摘要和实际执行一起更新。

例如，本轮开始时只有技能 A，过程中新增 B：本轮保持原技能列表，下轮出现 B。A 从第一版更新到第二版也是同样的过程。即使之前一个技能都没有，也会固定空列表，避免首次新增技能突然泄漏进正在运行的回合。

这里的“下一轮生效”是新技能已经可见、可调用，不是保证模型一定选择调用它。

## 10. 已经启动的沙箱怎么办

技能版本没变就继续复用；下一轮技能变了，沙箱需要重新创建，让实际挂载和技能说明一致。生命周期包装器也检查版本，所以不会因为外层一直复用旧实例而漏掉换版。

Docker 的工作区仍使用原来的持久化挂载，所以文件保留。云沙箱要先保存工作区，保存失败就不能贸然销毁旧实例。重建会重置运行中的进程、浏览器和 shell 内存状态，不能把“文件保留”说成整个运行现场无损迁移。云端路径本次没有真实服务端端到端验证。

## 11. 用户之间、外部修改和旧文件怎么处理

- 用户、Agent、会话分开组织缓存键；当前用户资料和所有者的默认资料分开查，避免混用身份。
- 技能开关和运行环境门控仍按当前配置判断，不能因为缓存而绕过限制。
- 安装、上传、技能管理、受控文件编辑走发布入口；正常健康链路下，下个回合可用。
- 任意 shell 手动修改不是同样保证。后台约 30 秒检查已注册的本地技能目录，发现外部变化再发布；直接改对象存储旧路径也不等于正式发布。
- 旧技能对象首次导入，删除的技能保留删除标记，避免被旧目录再次恢复出来。
- 老版本和未被引用的上传文件目前没有自动清理，目的是不误删活跃回合正在使用的版本；后续需要按留存规则回收。

## 12. 如何说明稳定性和收益

已经做过：跨客户端缓存更新/删除、通知失败后补偿、并发旧回填、会话冲突、技能上传失败、旧回合版本固定、新回合换版等测试，以及真实 Redis/MySQL 和 Docker 验证。

这次部署又检查了：资料与会话热读命中且不再读取对应源数据、更新后未等 TTL 即可见、真实沙箱/MinIO 往返与配额限制、健康检查和待补偿积压。

可以观察缓存命中、失败、拒绝回填、源读取计数和补偿积压；当前没有新建专门的监控面板。支持关闭 Redis 加速回到 SQL 读取，但已经发布的技能仍按新版本记录读取。

没有生产压测和模型端到端耗时对比，因此面试里说“减少重复的数据库和对象存储访问”，不要编造“整体快了多少倍”。代价是数据库写入增加版本/通知工作，技能历史版本也会占用空间。
